## 4.1 System architecture

The system is an offline batch pipeline, not a service. It reads four of the eight tables of the dataset (`studentVle.csv`, `vle.csv`, `courses.csv` and `studentRegistration.csv`) and checks the SHA256 and byte size of each against `inputs/manifest.json` before any use; a mismatch raises an error and stops the run. <!-- C4.1 --> It then builds one split per module presentation, fits and scores six models on that split, computes metrics and tests, and writes files. Figure 4.1 shows the flow and the module of the plan that owns each step.

*Figure 4.1. Architecture of the pipeline and the plan module that owns each step. Every arrow is a function call inside one process; nothing is exchanged over a network.*

```text
OULAD tables (read-only, hash-checked)         code/data.py
        |
        v
Module A   splits.py, features.py, foundation.py, provenance.py, leakage.py
           per-learner day-boundary split, cold-start cohort, date-bounded click weights,
           counted leakage assertions, fresh-process rebuild (rebuild_worker.py)
        |
        v
Module B   models.py, blend.py, cell.py
           six models and the learned blend weight, one "cell" per
           (presentation, split, condition, visible history k)
        |
        v
Module C   evaluate.py, stats.py, verdicts.py, variants.py, metrics.py
           metrics, paired Wilcoxon with Holm correction, verdicts for the six criteria
        |
        v
results/run_artifacts/<unit>/   +   results/run.log   +   results/run_receipts/<unit>.json

Module D   behaviour.py: descriptive features and K-Means segments; feeds no model
Module R   reproduce_phase1.py: re-runs the phase 1 pilot on one presentation (criterion C6)
```

Five design rules run through the code, and each one exists so that a criterion can be measured rather than asserted.

1. **One stage per process.** The entry point accepts exactly one stage, an artifact directory and the run log, each exactly once, with no default and no catch-all mode (section 4.3).
2. **Every fitted quantity is told which rows it may read and reports how many rows it read outside that set.** The count must be zero. This is what makes the leakage assertions L2, L3 and L9 of chapter 3 countable.
3. **Every assertion writes its measured count to an append-only log, zero included.** A count that differs from the required value is written first and then stops the run. A check that did not run is recorded as `unchecked` and never as passed.
4. **The test split is reached through one function that counts scorings.** Criterion C4's requirement that the test split is scored exactly once per model is therefore measured by counting the calls, not inferred.
5. **An artifact directory is immutable once written.** The entry point refuses a directory that already holds files, so a failed attempt cannot be overwritten by a later one and a receipt always describes one attempt.

### 4.3.2 The stage entry contract

Every execution goes through `code/main.py`. Table 4.3 gives the contract.

*Table 4.3. The stage entry contract of `code/main.py`.*

| Argument | Rule |
| --- | --- |
| `--stage pilot`, `main`, `iteration` or `diagnostics` | Required, exactly once, no default, no catch-all mode; one stage per process. |
| `--artifact-dir` | Required, exactly once, must lie under `results/run_artifacts/`, must be empty or absent. |

Invalid arguments exit non-zero before any file is created or any data is read. The first file written is `run_manifest.json` (stage, absolute paths, the argument vector, the exact command line, the seed, the SHA256 of the configuration and of the code tree, library versions and hardware); the last is `run_summary.json` (status, wall-clock seconds, `cpu_hours`, the count of each assertion and the list of unchecked items). The exit codes are 0 for success, 1 for an abort and 3 when criterion C6 is not met. <!-- C4.6 --> The G4 code gate tested the contract by execution and not by reading the README: nine calls, among them a missing argument, an unknown stage, a repeated stage, an artifact directory outside the allowed root, a wrong log path and a dry run, each behaved as the contract says, and after all nine `results/` did not exist. <!-- C4.7 -->

The stages do the following. `pilot` runs Module R (the phase 1 reproduction). `main` runs, for each of the 22 presentations, the foundation checks and then the evaluation. `iteration` is the same over the presentations named for it in the configuration, which is EEE_2014J only. `diagnostics` runs the post-hoc diagnostics of section 4.7 and decides no criterion.

### 4.3.3 What one main run does for one presentation

For each presentation the foundation stage rebuilds the population table and requires it to match the table of the protocol, checks the realised split fractions, runs the assertions on the split (L1, L4, L5), on the item features, and on the exclusion sets (L8), builds the fitted objects of every condition with their provenance records, and finally rebuilds the learner-derived objects in a fresh process and compares hashes (L7). The evaluation stage then runs 34 cells for the presentation: on each of the primary, secondary and tertiary splits, ten cells (the warm condition; condition A at k of 0, 1, 2 and 5; the robustness variant of A at k = 2; condition B at k of 0, 1, 2 and 5), plus two cells each for two narrow reruns of the primary split at learner thresholds of 3 and 10. <!-- C4.8 --> Each cell fits every model on the rows its condition allows, scores the test split once through the counting function, ranks with the fixed tie rule and computes the metrics. The primary split's warm and k = 2 cells of condition A decide C1 to C3; every other cell is reporting.

## 4.4 Pilot design and execution history

### 4.4.1 The phase 1 pilot

Before the experiment of this thesis, a pilot ran on one module presentation, outside any workflow engine and without receipts. Under the integrity rules it is prior evidence: it may be cited only as such, and only the part reproduced under a receipt (section 4.6.3) may be cited as a reproduced result.

The pilot chose its presentation by a deterministic rule, the one whose interaction count is closest to 400,000, which selects EEE_2014J with 402,947 rows. <!-- C4.9 --> It evaluated the 1,049 learners who had at least five distinct resources. <!-- C4.10 --> For each it held out a random 20% of the resources as the test set; the warm slice used the rest as visible history, and the cold-start slice used the same learners and the same test set with the visible history cut to the first two training resources. <!-- C4.107 --> Iteration 1 blended the two component scores with a fixed two-tier weight and trailed collaborative filtering on the warm slice by a relative gap of -19.9%. <!-- C4.11 --> Iteration 2 replaced it with a weight that grows with the number of visible resources, alpha = min(0.9, 0.2 + 0.05 x visible resources), and closed the gap to -2.7% relative to collaborative filtering while staying +341% relative to content-based filtering. <!-- C4.12 --> The pilot stopped at two iterations, on the stated ground that further tuning without a new mechanism would fit the threshold. <!-- C4.103 -->

The pilot was then repeated over all 22 presentations, and the first pass exposed a defect that stays in the record with its cause. In three presentations (BBB_2013B, DDD_2013B and DDD_2013J) the week fields of the resource table are missing for every resource, so the median of an empty column was undefined; the undefined values reached every content-based score and made the hybrid's Precision@10 equal that of content-based filtering to the last bit. <!-- C4.13 --> The defect moved the mean relative gain against collaborative filtering to -14.8% while the median stayed near -2.9%, and it was repaired by a fallback of 0.0 for a column with no known value. <!-- C4.14 --> After the repair, across the 22 presentations the hybrid trailed collaborative filtering on warm learners by a median relative gap of 2.7%, with a range of -10.8% to +0.9%. <!-- C4.15 --> It beat collaborative filtering in 3 of the 22 presentations, by at most 0.9%. <!-- C4.96 --> On the pilot's cold-start condition it beat content-based filtering in 22 of 22 presentations, by a median relative gain of +73.12% (range +13.55% to +163.85%). <!-- C4.16 --> The figure of +190% that the pilot summary attaches to its cold-start result is in fact the median warm-slice gain over content-based filtering (+189.54%, range +60.04% to +464.55%), and this thesis does not use it for cold start. <!-- C4.112 --> Against collaborative filtering on the same condition it lost in 22 of 22 presentations, by a median relative gain of -17.9% (range -29.1% to -10.0%). <!-- C4.17 --> The pilot summary states that the hybrid wins at cold start in 22 of 22 cases; that is true against content-based filtering only, and the summary also says the hybrid never beats collaborative filtering on warm users, which its own maximum of +0.9% contradicts. <!-- C4.108 --> Neither statement is repeated in this thesis. The pilot used about 30 seconds for one presentation and about 140 seconds for all 22. <!-- C4.18 -->

Two things bound what the pilot can be used for. Its numbers for the presentations other than EEE_2014J have never been reproduced under a receipt. <!-- C4.109 --> And its absolute values are not comparable with those of phase 2: the pilot's Precision@10 for collaborative filtering on the warm slice of EEE_2014J was 0.5352. <!-- C4.19 --> The receipted phase 2 value for the same presentation is 0.1877. <!-- C4.20 --> The two designs differ in the split, the treatment of click weights and the exclusion rule, among other things, and this thesis does not attribute the difference to any one of them.

The first design error that changed the population was the split. The first specification held out the last fraction of each learner's pairs and then extended the whole tied day into the test set, and recomputing it showed that this rule leaves 1,345 of 28,209 learners (4.8%) without a training or validation set. <!-- C4.31 --> It was replaced by the per-learner day-boundary split of chapter 3, which loses fewer learners. The second, and the largest for the criteria that can refute the hypothesis, was the cold-start oracle. The revision that answered cycle 0 excluded from every model's candidate list the learner's whole training and validation history while giving the model only k = 2 visible resources; a new learner is then ranked after roughly thirty of their later resources have been struck from the candidates. <!-- C4.104 --> A reviewer's probe on EEE_2014J at k = 2 measured cold-start Precision@10 of 0.2157 for global popularity under that rule against 0.0255 under the corrected one, an 8.5-fold inflation, and 0.1946 against 0.0333 for item-based collaborative filtering, a 5.8-fold inflation; under the oracle the two models were within 10.8% of each other where the corrected rule leaves collaborative filtering 31% above popularity. <!-- C4.32 --> The rule was replaced by a single principle: a learner's candidates exclude exactly what the learner has opened as of the moment of the recommendation. The two probe values under the corrected rule, 0.0255 and 0.0333, are the canary values of section 4.3.1. <!-- C4.5 -->

The repair of that error created the third: validation-time scoring used the exclusion set of the test moment, so validation Precision@10 was exactly 0.0000 by construction on 300 EEE_2014J learners against 0.1883 with training-only exclusion, and the blend label, the neighbourhood size and the regularisation constant would all have been fitted to an all-zero target without any assertion failing. <!-- C4.33 --> The fourth was found in the same cycle and had survived two reviews: click totals summed the clicks of all rows of a pair while only the pair's first date decided which slice it belonged to. On EEE_2014J, 17.8% of the clicks on warm training pairs are dated on or after the learner's test boundary, affecting 1,014 of 1,018 learners, and at k = 2 96.9% of the clicks carried by the two visible resources are dated after the second interaction, affecting 1,015 of 1,018. <!-- C4.34 --> A learner described as having two prior interactions was therefore weighted by their later engagement. The leak was asymmetric across the models, because global popularity counts distinct learners and reads no click, so only the content-based, collaborative and hybrid models carried it, which bears directly on the comparisons that decide C2 and C3. Every click weight now takes a date bound, a counted assertion (L9) reports the rows read from beyond it, and a second, independent check rebuilds each weight by truncation and compares hashes.

The code errors were of a different kind. The code had been compiled and its entry point checked, but nothing had been executed, and the first execution by a reviewer found defects that no reading had revealed: a positional subtraction that stopped every run on the first presentation and a counter that keyed a test scoring without the split name and would have failed at the end of a completed run, which is the worst place to fail. <!-- C4.35 --> The next cycle found an argument passed twice, which stopped the run on the first cold-start condition, and an attribute read that did not exist on the object that carried it. <!-- C4.97 --> The fifth blocker of the code review, in cycle 1, was not a code error but a methodology gap: two leakage assertions fire by design on the tertiary random split, which has no time bound, and a ruling was needed on how they are recorded; they are recorded as not applicable, with the measured count kept as evidence and never compared with the required zero, and they stay must-be-zero on every other split and in every cold-start condition.

The plan file that all this happened under did not change: `plan.md` hashes today to the value recorded in the protocol's header when the methodology stage began. <!-- C4.36 --> Chapter 3 states the resulting design; what this section adds is the record that the design was reached by reviews that found real errors, several of them large, before any result existed.

### 4.4.4 The scale-up decision and the phase 2 build

The pilot's own next step was a learned blend weight instead of a hand-picked formula, to find out whether the residual gap to collaborative filtering was a ceiling of linear blending or an imperfectly guessed constant. <!-- C4.37 --> The plan turned that into phase 2 with the mechanisms of Table 4.4. Because a result cited without a receipt is not acceptable evidence, the manager decided to reproduce the phase 1 pilot under a receipt first (section 4.6.3), at a cost the plan puts at about three minutes of CPU. <!-- C4.38 --> The plan's run budget is three runs: one reproduction, one main run over all 22 presentations, and one reserved for a named mechanism fix. <!-- C4.39 --> Three receipted runs were made: the reproduction, the main run and the post-hoc diagnostics run of section 4.7, which the candidate approved after the main run; that brings the count to the plan's maximum, and no rerun for a mechanism fix was made. The build was made in three parts to keep each within the engineer's line budget: part one for Modules R and A with the entry point and the assertions, part two for Module B, part three for Modules C and D. Where the protocol was silent the engineer chose a default and recorded it for the methodologist and the reviewers; the consequential ones are in section 4.5.

## 4.5 Phase 2 as realised in code

### 4.5.1 The models and the blend

Six models are scored in every cell: five seeded random rankings (seeds 42 to 46), global popularity, week-aware popularity, content-based filtering, item-based collaborative filtering and the hybrid. <!-- C4.102 --> Only the random model is stochastic; the others are deterministic. The hybrid scores a learner by `alpha * CF + (1 - alpha) * CBF`, where CF and CBF are the min-max scaled component scores over the candidate set, so **alpha is the weight on the collaborative component** and one minus alpha the weight on the content component. <!-- C4.42 --> Alpha is produced per learner by a logistic regression over eight learner-level features (visible-resource count, log of visible clicks, active days, the top-1 and top-10 score mass of each component, and the share of resources with missing week data), fitted on validation data only, with its regularisation constant chosen by stratified cross-validation within the validation learners. <!-- C4.43 --> The regression uses the lbfgs solver and an L2 penalty. The regularisation constant is chosen from four values (0.01, 0.1, 1 and 10), the label sweep runs on an eleven-point grid from 0.0 to 1.0, and the collaborative neighbourhood size is chosen from five values (10, 25, 50, 100 and all). <!-- C4.44 --> Alpha is the predicted probability, is in [0, 1] by construction, and is not clipped. <!-- C4.110 --> If fewer than 20 validation learners can be labelled, alpha is a constant. <!-- C4.45 --> The three columns that carry the behavioural proxy in the blend are the visible-resource count, the log of the visible clicks and the active-day count; the click-weighted profile of the content-based and collaborative components carries it too. Nowhere does the code use a duration, and no component is a session model.

### 4.5.2 Defaults chosen where the protocol was silent

Where the protocol did not fix a detail the engineer chose one and recorded it; Table 4.6 lists the ones that a reader repeating the experiment must know. They are not free parameters tuned on results: each was chosen before any result existed and is stated in `code/README.md` or in the protocol.

*Table 4.6. Implementation defaults chosen where the protocol was silent.*

| Item | Default |
| --- | --- |
| Collaborative neighbourhood | An item's neighbourhood keeps its own similarity plus its N most similar other items; N = all uses the full matrix with the diagonal |
| Popularity with no history | Week-aware popularity treats every resource as eligible when nothing is visible (k = 0) |
| Scaling and score-mass features | Min-max scaling and the top-1 and top-10 features are computed over the candidate set |
| Collaborative score | Not divided by the learner's click total, which is a per-learner constant |
| Validation day of the secondary split | The smallest day whose validation slice does not exceed 10% of the pairs, because the literal largest day gives an empty set |

### 4.6.2 How the receipts were made, and what that does and does not prove

The workflow engine of the repository (`ar-runtime/scripts/ar-workflow-engine.py`) imports the Unix module `fcntl` and cannot run on Windows, and the machine that ran this project is a Windows machine; this is also why the repository's Linux set-up script was not used. Two deviations were recorded at the start, before any run: D1, that the engine is unavailable, so the manager tracks the units by hand and every gate verdict is written to a file before a unit closes; and D2, that run receipts are assembled by hand from the real SHA256 of every artifact file, the exact command line, and an execution event hash computed by hand. <!-- C4.59 --> The event hash is the SHA256 of a canonical JSON object with the keys unit, cycle, stage, argv, started_at, finished_at, exit_code, run_log_before_sha256, run_log_after_sha256 and attempt_sha256, in that order. <!-- C4.60 --> The review tool that writes gate verdicts also shells out to the engine, so the reviewers wrote their verdicts by hand as files and said so in a notice at the head of each. <!-- C4.61 -->

What was made by hand is the receipt envelope, not the run: the entry point itself ran unmodified and wrote its own manifest, log, verdicts and summary, and the receipt copies from those files. What the hand-made receipts give a reader is checkability. The G5 reviewer re-hashed all 52 files of the pilot and main receipts against the files on disk and recomputed both execution event hashes from the receipts' own fields, and all of them matched. <!-- C4.62 --> What they do not give is an engine-issued proof that the recorded command was the command that ran; the manifest, the log and the file hashes agree with the recorded command line, and that agreement is the only cross-check there is. A receipt in this thesis is therefore evidence of consistency and not a signed attestation, and chapter 5 does not claim more for it. Where this thesis says a step "went through the engine", it means that the entry-point contract of section 4.3.2 was checked by hand against every property the engine's command contract would enforce; no engine call is claimed. <!-- C4.63 -->

The main run was launched as a background process, and the session that launched it reached a usage limit soon after; the process ran on and finished on its own. Its files were therefore re-verified from disk, first by the manager, then by the runner and then by the G5 reviewer, before any figure from them was used.

## 4.7 The two post-hoc diagnostics

After the main run the analyst identified two questions the criteria could not answer and asked for two diagnostics, and the candidate approved both on 2026-09-22. The first is a question the plan itself pre-registered as a risk: whether the learned blend weight converges near 1, which would mean that the content and behavioural components carry no usable marginal signal. <!-- C4.111 --> The second is that the hypothesis's third component, the behavioural signal, had never been tested on its own. Both use the approved code path, and neither decides a criterion.

They run as a fourth stage, `--stage diagnostics`, routed to `code/diagnostics.py`, and not inside the main stage, so the main run's cells, provenance records, leakage checks and criteria are unchanged; the stage's own `criteria_verdicts.json` reads `unchecked` for all six criteria by construction.

```text
.venv-pilot\Scripts\python.exe code/main.py --stage diagnostics --artifact-dir results/run_artifacts/u13d_diag_run --run-log results/run.log
```

**D1, alpha logging.** On condition A at k = 2 (the cell that decides C2 and C3), for every learner whose test set was scored, the stage records the blend weight the production hybrid actually used, the learner identifier and k, one JSON line per learner in `alpha_log_<presentation>.jsonl`. It wrote 22 such files holding 5,444 records in all, equal to the sum of the cells' scored-learner counts. <!-- C4.83 --> Alpha is the weight on the collaborative component.

**D2, behavioural-signal ablation.** A model variant, `Hybrid_ablated`, fits the same blend procedure (same regularisation grid, same cross-validation, same seed 42) over the feature matrix without the three columns that carry the behavioural proxy, the visible-resource count, the log of the visible clicks and the active-day count, and keeps the five others. It is scored on the warm cell and on the cell of condition A at k = 2 for all 22 presentations, next to the production hybrid, with the same metric function as the main run, and wrote 22 `ablation_<presentation>.json` files. <!-- C4.84 --> The diagnostics stage as a whole wrote 47 files and used 507.89 seconds of wall-clock time. <!-- C4.85 --> The ablation removes columns from the blend's own feature set; it does not remove a behavioural recommender component, because the hybrid has none, and it therefore does not test the behavioural clause of the hypothesis on its terms, which stays unchecked.

The code changes were small: one line in `Hybrid.score` stores the weight it used and nothing else, and the ablation switch defaults to off and is never turned on by any production caller. A reviewer at a reduced gate (G4-lite) checked the isolation and approved with no blockers and five warnings: the diagnostics code calls none of the functions that run the cells, the evaluation or the leakage checks, so it is criterion-blind by construction. <!-- C4.86 -->

**Disclosure.** Both diagnostics are post-hoc and score the test split a second time. The diagnostics stage calls the model's scoring function directly, outside the counter that enforces criterion C4's rule of one scoring per model, and scores the production hybrid a second time and the ablated variant once. The numbers are therefore second looks at the test split after the criteria were decided. They may not be used to revise any criterion, threshold, model or the frozen protocol, and every chapter that reports them says so. C4, as decided by the main run, is unaffected: the diagnostics ran in their own process with no counter. The diagnostics' results are in chapter 5.

## 4.9 What this chapter established, and what chapter 5 needs from it

This chapter established that the design of chapter 3 was realised in Python modules behind one entry point that accepts a single stage per process, that no deep model and no TensorFlow or Keras was used, and that the technology stack is Python with NumPy, pandas, scikit-learn and SciPy. It established the history of the pilot: a pilot on one presentation with 1,049 learners whose six recorded values were reproduced under a receipt with an absolute difference of 0.0. <!-- C4.89 --> Its 22-presentation figures remain prior evidence, and its cold-start reading had the hybrid ahead of content-based filtering and behind collaborative filtering in all 22 presentations. <!-- C4.90 --> It established that the design was corrected by reviews that found real defects before any receipted result existed, among them a cold-start oracle that inflated Precision@10 8.5-fold for popularity and 5.8-fold for collaborative filtering and click weights of which 17.8% post-dated the test boundary in EEE_2014J. <!-- C4.91 --> It established that three runs were receipted and that the main run used 1.0140 CPU-hours against a budget of 4.0. <!-- C4.92 --> The reproduction used 0.238 minutes against a budget of 15. <!-- C4.93 --> The deviations of the record are the hand-made receipts, the two code trees, the prefix hash of the shared log and the unreceipted pre-run tests. It established that the two diagnostics are post-hoc and decide no criterion.

It did not establish that the pipeline is free of leakage beyond the counted assertions, which are evidence and not proof, nor that another machine reproduces the numbers, nor that the receipts are engine-issued, nor any mechanism for the cold-start result. Chapter 5 needs from this chapter five things. It needs the receipted runs of Table 4.7 as the only source of results, with the diagnostics labelled as coming from a different tree and as post-hoc. It needs the criteria verdicts of the main and pilot receipts, with C5 combined by hand from both. It needs the leakage evidence to be cited as the assertions L7, L8 and L9 and not as the structurally zero field of C4. It needs the pilot's figures to be labelled prior evidence, except the six values reproduced for EEE_2014J. <!-- C4.89 --> And it needs its values to come from the per-presentation artifacts and not from the results summary's prose.
